# ADR-0002：和弦档位（Chord Dictionary）与局部重绘

> 状态：**已决定**
> 日期：2026-11-01
> 关联：`docs/adr/0001-neural-onnx-feasibility.md`（模型能力）、PRD §5.1（多重解释）、§4.8（编辑事务）
> 实测脚本：`neural/verify_chord_dicts.py`、`neural/probe_local_redecode.py`、`neural/probe_pad_min.py`

---

## 1. 背景

`lv-chordia` 提供三档 chord dictionary。用户要求 App 忠实提供，并允许**对某一段用某个档位重新分析**（默认 submission）。

需要回答两个问题：
1. 三档是什么？切换成本多大？
2. 「局部重绘」在技术上怎么做才正确？

---

## 2. 三档是什么：一套模型 + 三套 HMM 解码词典

**关键事实：三档不是三套模型，而是同一份网络输出配三套不同的 HMM 解码模板。**

实测（`Refrain`，290s）：

| 档位 | 模板行数 | 段数 | 实际用到和弦 | **HMM 耗时** |
|---|---|---|---|---|
| **submission**（默认） | 25 | 139 | 18 种 | **241 ms** |
| ismir2017 | 14 | 136 | 13 种 | 136 ms |
| full | 381 | 139 | 19 种 | **2037 ms** |

### 2.1 这带来的产品含义

**切档 = 只重跑 HMM，不重跑 CQT、不重跑 5 模型。**

| 阶段 | 耗时 | 切档时是否重跑 |
|---|---|---|
| CQT | 3.2 s | ❌ 否 |
| 5 模型 ensemble | 2.4 s | ❌ 否 |
| **HMM 解码** | **0.14 – 2.0 s** | ✅ 是 |

所以：
- `submission ↔ ismir2017` 切换只需 **136–241 ms**，**可以做实时预览**
- `full` 档需 **2 s**，需要进度提示（或只对选定区间解码）

### 2.2 档位差异的实质：不是「和弦进行」，是「记谱精细度」

实测前 20 秒：

| 时间 | submission | ismir2017 |
|---|---|---|
| 0.42 – 11.35 | `G:maj` | `G:maj` |
| 11.35 – 12.75 | **`D:maj/3`** | （合并进 G:maj） |
| 12.75 – 18.25 | `E:min7` | `E:min7`（完全相同） |
| 19.37 – 21.83 | **`C:maj/5`** | （合并成 `C:maj`） |

**`D:maj/3` 是 D 大三和弦第一转位。ismir2017 把转位/低音信息抹掉了。**

> **UI 必须说明这一点**。否则用户切换档位后看到「和弦变了」，会以为分析出错。
> 正确的文案是：「档位影响记谱精细度，不影响和弦判断」，并把差异高亮在**低音/转位**上。

### 2.3 各档定位（来自上游 README）

| 档位 | 定位 |
|---|---|
| submission | 通用，最佳平衡（默认） |
| ismir2017 | 研究对比用，更简单 |
| full | 爵士、复杂和声 |

## 3. 局部重绘：技术设计

### 3.1 核心原理

「局部重绘」= **对选定时间区间重跑 HMM 解码，结果替换该区间**。

因为 HMM 解码只需要模型输出（已缓存），重绘成本 = 区间长度 × 43.07 fps 的 Viterbi。

### 3.2 pad（上下文）实测结论

**这是本 ADR 最重要的一段，因为初版判断被数据推翻了。**

#### 初版判断（错误）

用严格指标（段数与边界毫秒级全等）测，得到「需要 10s pad」，甚至认为「前置/后置都要 10s」。

#### 实际测量（`neural/probe_pad_min.py`）

对最难的区间 `[250, 262]`，逐 0.5s 测 pad：

| pad | 不一致帧 | 不一致率 | 错误位置 |
|---|---|---|---|
| 0.0 | **2 帧** | **0.3%** | 距左端 **0.00–0.02s** |
| 0.5 | 0 | 0.0% | — |
| 1.0 – 8.0 | 0 | 0.0% | — |

**结论：误差只出现在区间起点 1–2 帧（20–40 ms），pad=0.5s 即可消除。**

#### 为什么初版测出「10s」

两条原因：

1. **指标过严**：`seg_match` 要求段边界毫秒级全等。边界落在 249.98 还是 250.02 会判为"不一致"，但听众完全无法分辨。
2. **左端帧对齐**：`[18, 25]` 区间在 pad=0 时只有 44.9%，因为 Viterbi 起点错误让边界落在 17.98（区间外），整段错位。而 `[250, 262]` 恰好对齐帧栅格，只差 2 帧。

#### Viterbi 的方向性

**误差只在起点侧**，右端从不出错 —— Viterbi 是前向解码，终点状态对整条路径的约束很弱。

### 3.3 决定：pad = 前后各 2 秒

虽然**只用前置 2s 就够**，但采用**前后对称各 2s**，理由：

1. **用户可见一致性**：右端 pad 避免「保留其一」对比时出现 1 帧级抖动
2. **曲首/曲尾**：靠近边界时自动截断，对称规则更简单
3. **成本可忽略**：多 4s 上下文对 Viterbi 无影响

```
给定用户框选 [a, b]（秒）
  decode_range = [max(0, a - 2.0), min(duration, b + 2.0)]
  只采纳 [a, b] 内的解码结果
```

### 3.4 接缝（seam）语义

用户框选 `[a, b]`，但原有和弦段边界不一定在 `a` / `b` 上。

**决定：允许切断原有片段，按 Tick 精确切。**

理由：若自动扩大到整段，用户就失去了「局部」的意义。PRD §3.2 要求所有事件是整数 Tick、半开区间，正好支持精确切分。

```
原有:   [18.25, 19.37] D:maj
框选:   [19.00, 21.00]
结果:   [18.25, 19.00] D:maj   ← 保留（被切断的前半）
        [19.00, 21.00] 新解码结果  ← 覆盖区
        [21.00, 21.83] 从新结果末尾到原边界 ← 保留（被切断的后半）
```

> ⚠️ **待确认**：接缝处是否要把新结果的边界**吸附到最近的旧边界**？
> 这一条建议在 Phase 1 用真实数据试后再定。当前实现按"精确切、不吸附"。

### 3.5 交互流程

```
1. 用户在时间轴上框选 [a, b]（任意区间，不限于段落）
2. 右键菜单 → 「用其他档位重新分析」
       显示三档，默认与当前档位一致
3. 后端：从缓存的模型输出切片 → 带 pad 解码 → 返回新区间结果
       进度：submission/ismir2017 即时（<250ms），full 需提示（~2s）
4. 前端弹出「局部重绘预览」：
       · 时间轴上高亮 [a, b]，新旧结果并排或叠色显示
       · 两个按钮：[覆盖]  [保留其一]
5. 用户选择后 → 作为一条编辑事务提交（可 Undo/Redo，落库）
```

### 3.6 「保留其一」的语义

**用户逐个片段选择，而不是整块二选一。**

因为「保留其一」通常用于「新结果大部分更好，但个别段旧结果对」的情况，整块二选一没有意义。

```
预览面板列出 [a, b] 内的所有差异段：
  ┌──────────────────────────────────────────┬───────┬───────┐
  │ 时间            │ 原结果      │ 新结果      │ 保留? │
  ├──────────────────────────────────────────┼───────┼───────┤
  │ 19.00 ~ 19.37   │ D:maj      │ D:maj/3    │ ○原 ○新 │
  │ 19.37 ~ 20.80   │ C:maj/5    │ C:maj      │ ○原 ●新 │
  │ 20.80 ~ 21.00   │ D:maj      │ D:maj      │ (相同)  │
  └──────────────────────────────────────────┴───────┴───────┘
默认：全部选「新」
```

### 3.7 数据模型：复用编辑事务，不新增表

**不需要新表。** 局部重绘就是一条 `edit_transaction`：

```json
{
  "type": "RewriteChordSegment",
  "op": "replace",
  "range": { "startTick": 18240, "endTick": 20160 },
  "dictionary": "full",
  "mode": "overwrite" | "pick_per_segment",
  "selections": [ { "startTick": ..., "endTick": ..., "source": "new" | "original" } ],
  "before": [ ...受影响的和弦事件快照... ],
  "after":  [ ...替换后的事件... ],
  "revision": 42
}
```

- `before` / `after` 完整快照 → 支持 Undo/Redo（PRD §4.8）
- 一次局部重绘 = **一条** Undo 步骤（不是每段一条）
- 走同一套 `revision` 乐观锁

### 3.8 必须缓存的中间数据

为了让切档/重绘零成本，必须持久化：

| 数据 | 大小（290s 曲目） | 必要性 |
|---|---|---|
| **CQT 特征** `(T, 288)` float32 | 12496 × 288 × 4 = **14.4 MB** | 高（重算 3.2s） |
| **模型输出** 6 头 `(T, C)` | 12496 × 100 × 4 = **5.0 MB** | 高（重算 2.4s） |
| 各档解码结果 | 139 段 × ~40 B = 6 KB | 低（可重算） |

**建议：缓存 CQT + 模型输出到磁盘（约 20 MB/首歌）**，符合 PRD §6.2「保存模型原始输出以便复盘」。

> 也可考虑压缩：CQT 和 logits 都用 fp16 存，体积减半，对精度无影响
> （后处理只是取 argmax/softmax，fp16 误差远小于阈值）。

## 4. 对 ROADMAP 的影响

### 4.1 M4 需要新增的任务

| 任务 | 说明 |
|---|---|
| 4.x-a | 三档字典加载（三个模板文件随包分发，共约 5 KB） |
| 4.x-b | **按档位切换解码**（复用模型输出，不重跑前处理） |
| 4.x-c | **局部重绘**：区间切片 + 前后 2s pad + 接缝裁剪 |
| 4.x-d | **差异计算**：新旧结果按 Tick 对齐，生成 diff 列表 |
| 4.x-e | 缓存 CQT + 模型输出到磁盘（fp16，约 10 MB/首） |

### 4.2 M7（Rust 移植）需要额外注意

- HMM 解码器要支持**从任意帧范围开始解码**（而非全曲）
- 必须在 Rust 侧保留「模型输出可切片」的能力（不能只输出最终和弦段）

### 4.3 对 PRD 的增补

PRD §6.5 只提到 `draft / confirmed / rejected` 三态。局部重绘后：

- 重绘产生的段 → `draft`（需确认）
- 用户「保留原结果」的段 → 保持原状态（可能是 `confirmed`）
- **重绘不应覆盖已 `confirmed` 的段**，除非用户在预览中显式选择

> 这一条与 PRD §6.5「重跑 AI 不覆盖已确认和弦（B03）」一致，
> 局部重绘应遵循同一规则。

## 5. 待确认事项

| # | 事项 | 建议 |
|---|---|---|
| 1 | 接缝是否吸附到旧边界 | 先不吸附（精确切），Phase 1 用真实数据体验后再定 |
| 2 | full 档 2s 是否可接受 | 只对选定区间解码后，full 档在 10s 区间上只需约 70ms，可接受 |
| 3 | 模型输出缓存格式 | fp16 `.npy` 或自定义二进制；Rust 侧用 `ndarray` 读 |
| 4 | 是否允许「换档重解全曲」 | 应允许（submission 全曲 241ms，full 2s），但默认走局部 |
