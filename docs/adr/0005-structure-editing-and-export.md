# ADR-0005：结构编辑、级数轨派生，与两种导出格式

> 状态：**已决定**
> 日期：2026-11-01
> 关联：`client/src/timeline/domain/SectionLabels.ts`、`client/src/components/TimelineView.vue`、
> `client/src/timeline/interaction/useClipEditing.ts`、`client/src/export/exporters.ts`、
> `client/src/api/backend.ts`
> 触发：用户要求「结构段 CRUD 实装」「段可带调性、级数轨高亮对应行」「导出讲解 + .fbsong」

---

## 1. 结构轨需要独立的编辑能力

### 问题

结构轨和和弦轨原来**共用一套右键菜单**，于是结构段右键出来是
「在此新建和弦」「编辑和弦名」「用其它档位重新分析此段」—— 对结构段全是错的语义，
而真正需要的「设置这段的调性」根本没有入口。

同时「用户改过的结构」无处可存：模型产物在 `analysis.sections`，
而 `SongEdits` 里只有 `key` / `degreeTracks` / `chordEdit`。

### 决定

**结构轨的菜单按轨道类型分派**（`sectionMenuItems`）：

```
在此新建结构段        默认 8 小节，不越过曲末
重命名…              弹字典选择器
─────────
设置此段调性…        复用 KeyPicker
清除此段调性
─────────
在播放头处拆分 / 与下一段合并
─────────
恢复为 AI 结构
删除此段
```

**结构名称只能从字典选，不能自由输入**（`SectionLabels.ts`，34 个词 / 5 组）：

| 组 | 内容 |
|---|---|
| 主体 | Intro, Verse, Pre-Chorus, Chorus, Post-Chorus, Bridge, Outro |
| 过渡 / 变体 | Pre-Verse, Refrain, Hook, Tag, Turnaround, Coda |
| 器乐 | Riff, Solo, Guitar Solo, Keyboard Solo, Instrumental, Interlude, Vamp |
| 电子乐 | Build-up, Pre-drop, Drop, Breakdown, Main, Groove, Break, Fill, Vocal Chop |
| 收尾 | Ending, Fade in, Fade out |

理由：结构名是**分析用语**。同一首歌出现 `Chorus` / `chorus` / `副歌` / `高潮`
四种写法，等于没有结构信息，后续无法按结构做统计。和「和弦名只能从
ChordPicker 选」是同一个道理。

**显示名用英文原词，中文只做悬停提示**。`Pre-Chorus` 的中文译法业界不统一
（预副歌 / 导歌 / 副歌前段），拿它当显示名会让两个人对同一份谱面产生不同叫法。

`normalizeSectionLabel` 负责把模型输出（`verse` / `Verse 1` / `Chorus2`）
归一成标准写法；**认不出的原样保留**，宁可显示陌生标签，也不能悄悄改成别的段落。

### 存储

```ts
SongEdits.sections = {
  clips: { id, startTick, endTick, label, key?: { tonic, mode } }[]
}
```

用 tick 而不是 bar，因为用户可以拖到半小节。

**和 `chordEdit` 的关键区别：不绑分析指纹。**
和弦是模型产物，重新分析后新结果通常更可信，所以旧编辑该失效；
**结构是人工判断**（用户亲手划的段、标的调性），不该因为重跑一次模型就被覆盖。
想回模型结果走「恢复为 AI 结构」。

## 2. 段调性：只作提示，不改计算（模式 A）

### 需求

用户要给结构段标调性（例如 Chorus 是 G 大调），含义是
「**这段转调了，得按 G 大调那条级数轨来理解**」。
并明确要求：**高亮作用在块级别**，用来说这句话。

### 决定：模式 A（只提示）

“段调性参与级数计算”是另一个选项（模式 B），但**没采用**：
自动换调会让级数块在段边界突然跳变，用户反而看不懂自己看到的是哪个调的数字。

高亮规则（`shouldHighlightDegree`，三条互斥）：

| 段调性 | 主级数轨（自动轨） | 自定义轨 |
|---|---|---|
| **没标** | ✅ 高亮（它是这段的默认解读） | ❌ 不高亮 |
| 标了，且与该轨调性一致 | ✅ | ✅ |
| 标了，但没有任何匹配的轨 / 调性不符 | ❌ | ❌ |

两条来自用户的明确要求：
- 「段标了 G major 但没有匹配的级数轨，可以不高亮任何轨道」——
  硬挑一条会让用户误以为「系统认为这段就是这个调」
- 「如果啥都没标，主级数轨（级数解释）要高亮」——
  语义是「这段没有特别标注，那就按全局调性理解」，而主级数轨正是跟随全局的那条

视觉上用**主题色实底 + 白字**（`--accent`），不用描边/发光：
12px 高的块里描边几乎看不见，而这是个强提示，必须一眼分辨。
结构块右上角显示 `G` / `Gm` 小徽章。

## 3. 级数轨：完全从和弦轨**实时派生**

### 问题

级数块原来是「生成轨道时建好的一批空壳块」（`makeDegreeTrack` 遍历和弦，
每个和弦配一个 `parentId` 指向它的空块）。于是：

```
用户手动新建一个和弦块 → 和弦轨多了一块
                      → 级数轨还是生成时那批空壳 → 没有对应块 → 那片区域空白
```

### 决定

级数是**纯派生数据**（数字 = 父和弦 + 调性），它自己没有独立内容。
渲染时**遍历当前和弦轨的每一个块，当场算一个级数块**：

```ts
if (isDegreeTrack) {
  for (const cc of chordClips) {
    out.push({
      id: `${track.id}::${cc.id}`,                    // 稳定 id，选中态靠它
      label: chordToNumber(cc.label, tonic) ?? '—',
      ...editing.projectedRange(cc)                    // 时间直接跟父和弦
    });
  }
  return out;
}
```

四个动作全部自动同步：新建 → 出现；删除 → 消失；拖动 → 跟随；改名 → 重算。

### 多条级数轨各自算数字

一条级数轨只能表达**一种**调性视角，但实际分析经常要同时看几种：
关系大小调对照（A 大调里 `F#:min` 是 vi，F# 小调里它是 i）、转调段、学习对照。

所以每条级数轨把调性存在**自己身上**（`RealTrack.degreeTonic` / `degreeMode`），
渲染时用 `degreeTonicOf(track, 全局)` = 轨道自己的 > 全局 > 空串。

> 曾经的 bug：渲染层一律读全局 `keyTonic`，于是所有级数轨算出同一套数字 ——
> 表现为「改了徽章（调号）但数字没变」。用户的原话是
> 「级数轨根本没有单独计算，却换全曲的主调，自定义级数轨跟着变」。

只有「级数解释」那条自动轨**故意**没有 `degreeTonic`，它本来就该跟随全局。

## 4. 两种导出，定位完全不同

| 格式 | 给谁 | 牺牲什么 |
|---|---|---|
| **导出讲解** → Markdown | 人看（笔记、分享、教学） | 丢掉几乎所有精度（tick、概率、备选） |
| **导出 .fbsong** → 完整 JSON | 程序看（备份、迁移、再导入） | 不牺牲 —— 一个字段都不裁 |

所以是**两个并列按钮**，不是一个「导出」加格式下拉：
用户点的时候心里已经明确「我要给人看」还是「我要备份」。

### 讲解稿的组织原则：先结论后明细

```
标题 + 概览（BPM / 调性 / 小节 / 和弦段数 / 时长）
调性（自动 or 手动；调音偏离提示；鼓组相位体检）
结构表（段落 / 小节区间 / 时间）
和声进行（按结构段分组，和弦 + 级数，连续同和弦合并成 ×N）
统计（和弦段数、根音分布）
```

不是把 `analysis.json` 排版成表格 —— 那是「数据导出」，不是「讲解」。

### `.fbsong` 是纯文本 JSON

```json
{
  "format": "fbsong",
  "version": 1,
  "exportedAt": "...",
  "analysis": { ...analysis.json 全部字段... },
  "edits":    { ...SongEdits 全部字段... },
  "view":     { "key": {...}, "bpm": 90.2 }
}
```

2 空格缩进、**不压成一行**：出问题能用记事本打开看、能被别的脚本处理、
git diff 也读得懂。压缩二进制省的那点体积不值得。

`format` + `version` 让以后改结构时能识别旧文件。

### 写文件不走 plugin-fs

导出只需要「写一个文件」，为它引入整个 fs 插件（外加一套 scope 配置）不划算。
Rust 侧加一个 18 行的 `write_text_file`，路径由 `dialog.save()` 给出 ——
**那是用户亲手选的位置**，不需要再做目录白名单。父目录不存在会自动创建
（Windows 的保存对话框允许用户选一个还没建的子目录）。

## 5. 用户编辑必须落盘（会话级）

「所有可保存的信息都是会话级的」（用户原话），所以：

- 编辑**按歌曲隔离**：`songEdits: Record<songId, SongEdits>`
- 落盘到 `analyses.edits_json` **且**同时写 `songs/<id>/edits.json`
  （可移植副本，一首歌的所有信息在同一目录）
- **惰性写盘**：拖动中不写（`gesture.kind !== 'none'` 时跳过）、
  1.2s 防抖、内容去重、切歌/窗口隐藏时强制刷

### 编辑层重建的粒度

不能一律 `resetTracks`：级数轨是派生数据，改它不该清掉用户在和弦轨上的编辑和撤销历史。
所以分两级：

- **换数据**（切歌 / 分析结果推进）→ `resetTracks`（清选中、手势、撤销历史）
- **只换级数轨**（改调性 / 加删轨）→ `syncDerivedTracks`（只替换 degree 轨）

判定依据必须是**分析指纹**（`${songId}:${拍数-小节数-和弦段数-时长}`），
不能用 `tracks` 结构 —— 那里面含用户编辑，会形成「编辑 → 重建 → 丢历史」的循环。

### 绝不在加载中途「自动清空」编辑

原来有一句 `if (same) patchCurrentEdits({ sections: undefined })`：
「内容和模型原始数据一样 = 用户撤销了所有编辑，顺手清理」。

它隐含一个致命前提：**编辑层里的内容一定是用户真实看到的**。
但加载期间 `data`（异步）可能先到、`edits`（异步）后到，编辑层会被短暂灌成
模型数据 → emit → 判定 same → **把已落盘的编辑删掉**。

用户看到的现象就是「改过的结构，一重启又回来了」。

所以：**自动判定一律不删**，清空只走显式的「恢复为 AI 结构」入口。
同时 `editKey` 在编辑层未就绪时返回**恒定值**（`${id}:pending`），
不让 data 加载引起中间态重建。

## 6. 遗留

- `.fbsong` 目前**只能导出，不能导入**。它是备份/迁移载体，但还不能回灌。
- 结构段的「恢复为 AI 结构」会丢掉所有段调性标注（整份快照替换），
  没有「只恢复段落划分、保留调性」的粒度。需要时再加。
- `dictionary`（和弦词典档位）仍是全局 ref，切歌会保留上一首的选择，
  是否符合「会话级」原则待确认。
