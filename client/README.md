## 关键设计决定

### 1. 权威是 Tick，秒是投影

用户的编辑操作以 **Tick** 记录。改 BPM 锚点后，已确认事件的 Tick **不变**，
只有它们的秒位置按新映射重算（PRD A12）。

若反过来以秒为权威，改一次速度全谱事件都会漂移。

### 2. Viewport 是不可变快照

Canvas 和 DOM **消费同一个 Viewport 对象**，都调用 `tickToX()`。
这是 A09（轨间对齐 ≤ 1px）能成立的根本原因——不是"小心对齐"，
而是"只有一个坐标来源"。

### 3. 校验抛错而不是兜底

`assertTick(1.5)` 直接抛 `TypeError`，不返回四舍五入结果。
坐标错误会一路污染到 Snap → 约束 → 存储，越早暴露越好。

### 4. 空区间不与任何区间相交

`intersects([500,500), [0,960))` 必须是 `false`。
朴素的 `a.start < b.end && b.start < a.end` 会误判为 true——这是实测发现的 bug。

### 5. 缩放锚点用反解而不是增量

```ts
// 先记住锚点 tick，缩放后反解 scrollTick
const tickAtAnchor = xToTickFloat(vp, anchorX);
const nextScroll = tickAtAnchor - (anchorX - offset) / nextPPT;
```

连续 20 次放大 + 20 次缩小后，锚点位置精确回位（实测 ≤ 5e-6px）。
若用增量累加，误差会累积。

| 项 | 规则 | 原因 |
|---|---|---|
| **圆角** | **一律 0**（只有头像/状态点用 50%） | 用户明确要求；工具类界面用直角更利落 |
| **主色** | `#FD651A` 橙 | 设计稿左侧激活菜单 / 播放按钮实测色 |
| **段落色** | 按名称取色，不是统一色 | Verse `#FDDDCC` / Pre `#FCDAC8` / Chorus `#FDB08B` / Bridge `#D9C9FC` |
| **和弦块** | 默认 `#F7F7F7`，选中 `#FDD8BD` + 橙边 | 中性底色让文字优先，橙色集中表达"选中" |
| **可见性切换** | **不要** | 用户明确说不需要；轨道可见性属于视图配置，不该占用轨道头空间 |

### 标尺

标尺在**轨道上方**（不是底部），高 30px，包含三层信息：

```
小节号（1 2 3 4 …，顶部 3px 起）
  ↓  每 4 小节加粗 + 深色
弱拍刻度（6px，从基线往上）
强拍刻度（11px，小节起点）
底部基线（1px）
```

- 缩放自适应：小节号按 `1/2/4/8` 小节稀疏显示
- 拍刻度在 `每拍 < 6px` 时自动隐藏（避免变成灰块）
- 播放头用橙色竖线贯通标尺 + 底部三角

### 对齐的保证方式

标尺、轨名列、内容区三者的对齐不是"调出来的"，而是：

1. CSS Grid：`grid-template-columns: var(--track-header-width) 1fr`，`grid-template-rows: var(--ruler-height) 1fr`
2. Canvas 与 DOM 都调 `tickToX(vp, tick)`，**单一坐标来源**
3. 轨名列与内容行**高度逐一相同**（实测 `[42,42,52,42,42,42,42]` 完全一致）

验证脚本：`scripts/check-interaction.ts`（滚动/缩放/播放 7 项）与 `scripts/shot.ts`（截图 + 元素统计）。

## 时间与节拍模型（用户确认的版本）

这是本项目与常见 DAW/PRD 最大的差异点，**以 beat 为最原始单位**：

### 1. 格子间隔恒定，拍号只改分组

```
4/4:  |· · · ·|· · · ·|     一小节 4 格
3/4:  |· · ·|· · ·|         一小节 3 格
6/8:  |· · ·|· · ·|         一小节 3 格（6 个八分 = 3 个四分）
```

- `CELL_TICKS = 960`（1 个四分音符）是**视觉与吸附的格子**，与拍号无关
- 拍号只决定「花多少格画一个小节线」
- 好处：变拍后网格密度不突变，缩放/吸附手感稳定

代码：`domain/MeterMap.ts` 的 `cellTicks()` / `barTicks()` / `beatLinesInBar()`

### 2. BPM 锚点，不是每小节存 BPM

```ts
type TempoAnchor = { tick: number; bpm: number };   // 稀疏，只在变化处存

barDurationSec = beatsInBar × (60 / bpmAt(barStartTick))
```

- BPM 指**四分音符每分钟**，与拍号无关
- 4/4 变 3/4 且 BPM 不变 → **一拍时长不变，小节变短**
- 变速 → 一小节内所有拍等比拉伸

代码：`domain/TempoMap.ts`（权威是 `{tick, bpm}`，`{tick, sec}` 是派生缓存）

### 3. 拍号 / 速度是顶部 tag 轨

不在主轨道区里，而是标尺下面两行 tag：
- **拍号** `4/4` —— 只标注变化点
- **速度** `♩ = 79.0` —— 每个锚点一个圆点

## 编辑交互

| 操作 | 手势 | 行为 |
|---|---|---|
| **移动** | 拖块体 | 整体平移，长度不变 |
| **单边 Resize** | 拖左/右边缘 | 只改一侧，另一侧不动 |
| **接缝联动** ⭐ | 拖两块之间的立缝 | **左块变长、右块变短**，边界保持重合 |
| **就地编辑** | 双击块 | 出现输入框，Enter 提交，Esc 取消 |
| **新建** | 双击空白 | 新建 1 小节 |
| **删除** | Delete 或右键 | 留下空隙，**不回填邻居**（`N 无和弦` 也是合法状态） |
| **撤销/重做** | Ctrl+Z / Ctrl+Shift+Z | ≥100 步，拖动只产生一条命令 |
| **取消拖动** | Esc / pointercancel | 恢复拖动前快照 |

### 量化规则（用户明确要求）

> 「拖动伸缩不能无限细分，要量化，最少是按一拍量化」

- `MIN_QUANTUM_TICKS = 960`（1 拍）
- 即使按住 **Alt 关闭吸附**，结果仍量化到 1 拍
- 任何块的长度 ≥ 1 拍

**为什么不能靠吸附保证**：吸附失败时（离网格太远）会返回 `Math.round` 的原始值，
拖出 1/3 拍这种碎片。所以 `snap()` 的**每一条返回路径**都强制量化。

### 级数解释：时间只读、文本可编辑

按 PRD §4.7「修改解释文本不会移动父和弦」：

| 属性 | 可编辑 |
|---|---|
| 时间范围 | ❌ 由父和弦投影 |
| **文本**（`IVmaj7` → `Imaj7`） | ✅ |
| 调性层归属 | ✅ |
| 删除 | ✅ |

级数轨上的拖动被 `ConstraintEngine` 拒绝（`degree.movable = false`）。

## 级数解释跟随父和弦（投影，不是同步）

用户问：「级数解释可不可以跟随绝对和弦的编辑走？」**可以，而且不该靠同步实现。**

### 两种做法

```
❌ 同步：级数块存自己的 startTick/endTick
   改和弦 → 额外去改级数 → 要处理拖动/Resize/接缝/拆分/合并/撤销
   漏掉任何一条路径，级数块就"飘在原地"

✅ 投影：级数只存 parentId，时间范围实时从父和弦算
   零同步代码，天然跟随；撤销时父和弦回退，级数自动回退
```

### 实现

```ts
interface ClipState {
  // 级数解释用这个字段声明"我解释哪个和弦"
  parentId?: string;
}

// 渲染时投影，而不是读存下来的 tick
function projectedRange(clip: ClipState): TickRange {
  if (!clip.parentId) return rangeOf(clip);
  const parent = clipById(clip.parentId);
  return parent ? rangeOf(parent) : rangeOf(clip);
}
```

关键点：`rangeOf(parent)` **已经包含拖动中的预览值**，所以拖动父和弦时级数实时跟随，不需要任何额外代码。

### 各种编辑下的行为

| 操作 | 级数行为 |
|---|---|
| 移动 / Resize 和弦 | 自动跟随（投影） |
| **接缝拖动** | 左右两个和弦各带自己的级数，都跟随 |
| 撤销 / 重做 | 自动回退（父和弦回退即可） |
| **拆分和弦** | 级数留在**左半**（原 id 保留给左半，右半变 draft） |
| **合并和弦** | 保留左块的解释；右块的级数**级联删除** |
| **删除和弦** | 级数**级联删除**（否则变孤儿，没有时间锚点） |
| 级数轨上拖动 | ❌ 拒绝（时间只读，PRD §4.7） |
| 改级数文本 | ✅ 允许（不影响父和弦） |

### 踩到的坑

**删除命令的快照必须包含级联删除的全部实体。**

第一版用 `makeDeleteCommand(chord)`，快照里只有和弦本身。结果撤销时和弦回来了、级数永久丢失。改成 `makeDeleteManyCommand([chord, ...children])`。

> 通用教训：**只要一个操作会连带修改其他实体，快照就必须覆盖全部受影响实体**，
> 否则撤销会留下脏数据。这也是为什么 `EditCommands` 用「全量快照」而不是「增量 patch」。

## 量化：为什么必须"边界独立量化"

用户要求「最小量化是一拍，实际编曲中不可能有人切换的这么快」。

模型输出是连续秒数，换算成 tick 后是任意值（如 14132）。导入时必须吸附到 1 拍网格。

### ⚠️ 踩坑：用 `Math.max(prevEnd, quantize(start))` 会导致**漂移累积**

```ts
// ❌ 错误：前一块量化后变长 → 后一块起点被推着走 → 一路传下去
const startTick = Math.max(prevEnd, quantize(s.start));

// ✅ 正确：所有边界独立量化，相邻块共享同一个边界值
const bounds = segs.map(s => quantize(s.start));
bounds.push(quantize(lastEnd));
for (let i = 1; i < bounds.length; i++) {
  if (bounds[i] <= bounds[i-1]) bounds[i] = bounds[i-1] + PPQ;  // 只修正冲突处
}
```

**症状**：截图上能看到块边界逐渐偏离小节线，越往后偏得越多。

**原因**：`Math.max` 把误差传递给了下一块，n 块之后累积偏差可达数拍。

**验证**：`scripts/check-all.ts` 断言「所有边界都是整拍」+「相邻块边界完全重合」。

## 和弦边界对齐小节（第三版量化）

用户反馈「量化还是飘」。排查后发现三层问题，逐层修掉：

### 问题 1：测量工具截断了网格线（不是产品 bug）

前几版验证脚本只取了前 30 条网格线，导致 400px 之后的块被误判为"偏差 296px"。

**修正**：取全部网格线，且只检查可见范围内的块。实测**可见范围内所有边界偏差 0.00px**。

### 问题 2：吸附到小节后产生 1 拍碎片

模型输出的和弦边界常落在小节中间（实测 3.56 / 4.25 / 6.25 小节），
但实际编曲中和弦几乎都在**小节起点**变化（对照 Song Master Pro 的结果可佐证：它的和弦全在 bar 1/3/4/5/6 起点）。

开启 `snapToBar: 0.45` 吸附后，相邻两个边界常吸附到同一个小节线 → 冲突 → 后一个被推后 1 拍 → **产生大量 1 拍碎片块**，视觉上就是"块很碎、边界飘"。

**修正**：吸附后**去重**（相同边界只保留一个，相当于合并两块），再做最小长度检查。

### 问题 3（**修错了，已回滚**）：曾把最小和弦长度设成 2 拍

第一版我把 `minBeats` 设成 2，理由是你的话「实际编曲中不可能有人切换的这么快」。

**这个理解错了**：你说的是 **0.08s 那种碎片**，不是 1 拍的**经过和弦**。

结果 `D:maj/3`（即 `5/7`，D/F#）、`Esus4` 这类经过和弦被整体吃掉，
而这些是**真实存在的音乐信息**（Song Master Pro 的 `5/7` 也只有约 1 拍）。

**修正**：`minBeats` 改回 1，且**默认不做小节吸附**。经过和弦完整保留。

### 结论：导入时不做任何"美化"

| 做法 | 结果 |
|---|---|
| ❌ `snapToBar: 0.45 + minBeats: 2` | 整洁但**丢失经过和弦** |
| ✅ `snapToBar: 0, minBeats: 1` | 保留模型原始边界（只量化到 1 拍） |

「整理碎片」应该是**用户主动触发的可选操作**（右键菜单），不能默认强加。

### 附带修复：窄块不显示名字

1 拍的经过和弦只有 17px 宽，原来的 24px 阈值导致**不渲染标签**，
看起来就像"和弦被吃掉了"。

**修正**：阈值降到 12px，窄块用 10px 字号 + 2px padding，`C:maj/5` 至少显示成 `C:ma…`。

### 最终效果

```
结构轨: Intro(0-2) | Verse(2-7) | B(7-11) | A(11-14)
         边界: 0.00    2.00        7.00      11.00   ← 全在整数小节

和弦轨: G:maj(0-4) | E:min7(4-6) | C:maj/5(6-7) | D:maj(7-8) | G:maj(8-12)
         边界: 0.00    4.00        6.00         7.00       8.00   ← 全在整数小节
```

两条轨的边界**互相对齐**（Verse/B 的切换点 7.00 同时是 D:maj 的起点）。

### 三个量化参数的语义

| 参数 | 默认 | 含义 |
|---|---|---|
| `MIN_QUANTUM_TICKS` | 960（1 拍） | 拖动/缩放的**最小粒度**，Alt 关吸附也生效 |
| `snapToBar` | 0.45 小节 | 导入时把边界吸到最近小节线的容差（防碎片用） |
| `minBeats` | 2 拍 | 导入时的**最小和弦长度**，短于此并入前一块 |

> 注意 `MIN_QUANTUM_TICKS`（交互粒度）和 `minBeats`（业务最小长度）是**两个概念**：
> 前者管"拖动时能不能拖到半拍"，后者管"和弦短到多少就该被合并"。

## 结构轨的"飘"：同色块看不出边界

用户反馈「开始和结束位置飘了」。

**实测数据是**：结构轨相邻块 `tick 间隙 0`、`像素间隙 0.0px`——**没有任何空隙**。

真正的问题是**视觉**：

| 现象 | 原因 |
|---|---|
| 结构块连成一片，看不出 B 在哪结束 | 所有段落用同一个背景色（`sectionColor` 对 A/B/C 走默认分支） |
| 看起来像"一个大块被切开" | 边框只有 1px，同色背景下几乎看不见 |

### 修法

1. **按段落名分配不同色相**（参照 Song Master Pro）：

| 段落 | 颜色 |
|---|---|
| Intro | `#FDE8D0` 米黄 |
| Verse | `#FBE3A8` 黄 |
| **A** | `#FFD9B0` 橙 |
| **B** | `#D6E4F7` 蓝 |
| **C** | `#CFE8DC` 绿 |
| Bridge | `#D9C9FC` 紫 |
| 待标注 | `#EFEFEF` 灰 |

2. 边框 `rgba(0,0,0,0.1)` → `0.14`

现在相邻段落的色相不同，边界一眼可见。

> **教训**：数据正确 ≠ 视觉正确。
> 「位置飘了」这类反馈要先量数据（tick / 像素间隙），
> 数据没问题再查**渲染**（配色、边框、层叠），不要一上来就怀疑量化。

## 量化单位：八分音符（480 tick）

用户最终确认：「和声量化以八分音符会好一些，因为有些歌会抢拍」。

### 两版演进

| 版本 | `MIN_QUANTUM_TICKS` | 理由 |
|---|---|---|
| 初版 | 960（1 拍） | 「不能无限细分，最少按一拍量化」 |
| **当前** | **480（八分音符）** | 「有些歌会抢拍」——切分和弦真实落在半拍位置 |

### 为什么八分音符是对的

- **切分和弦（syncopation）真实存在于半拍位置**，量化到整拍会把它抹掉
- 再细没有音乐意义：1/4 拍（240 tick）超出人耳对和声变化的辨识精度，模型也做不到
- 实测模型碎片是 0.08s ≈ 1/10 拍，八分音符网格天然吸收

### 实测效果（Refrain 前 12 块）

```
★半拍  G:maj    0→13920   14.50拍   ← 模型检测到和弦在 14.5 拍变化
★半拍  D:maj/3  13920→15360  1.50拍
整拍   E:min7   15360→22080  7.00拍
★半拍  D:maj    22080→23520  1.50拍
★半拍  C:maj/5  23520→26880  3.50拍
```

统计：**8 个边界在切分位置（半拍）**，4 个在整拍，全部对齐 480 网格。

如果还是整拍量化，那些 `.50` 的边界会被强行抹成整数拍，丢失真实的切分信息。

### 两个概念必须区分

| 概念 | 值 | 管什么 |
|---|---|---|
| **量化粒度** `MIN_QUANTUM_TICKS` | 480（八分音符） | 边界**能落在哪**（切分位置） |
| **最小长度** `minBeats` | 960（1 拍） | 和弦**至少多长**（防碎片） |

边界可以对到半拍，但和弦本身至少持续 1 拍。两者独立。

## 变速检测：half-time 漏检的识别与补全

用户提供变速曲目 `69910425165.flac` 并指出 **「65 = 130/2」**。

### 症状

beat_this 输出的 BPM 在中位 65 和 130 之间交替（正好 2 倍）：

```
小节   0 (t=  2.4s): 64.86 BPM
小节  20 (t= 76.2s): 129.03 BPM   ← 突然翻倍
小节  40 (t=120.5s): 65.04 BPM    ← 又回来
小节  50 (t=153.8s): 130.43 BPM
```

**表面上像变速，实际是 half-time 漏检**：模型在某些段落把 2 小节当 1 小节。

### 交叉验证（关键）

| 模型 | downbeat 间隔 | BPM | 小节数 |
|---|---|---|---|
| **all-in-one** | **1.850s** | 130 | 153 |
| beat_this | 1.850s / 3.62s 各一半 | 65 / 130 | 102 |

3.62 ÷ 1.85 = **1.96 ≈ 2** —— beat_this 漏检了一半 downbeat。

### 修复：`fill_half_time_gaps()`

```python
base = percentile(ioi, 15)          # 较短那一层（1.85s）
for 每个间隔 gap:
    n = round(gap / base)
    if n >= 2 and |gap - n*base| < base*0.25:   # 接近整数倍 → 漏检
        均分插入 n-1 个点
```

**保守判定**：只有「接近基础间隔整数倍」才补。真实变速的间隔不是整数倍关系，不会被误补。

### 补全结果

```
385 拍 / 102 小节  →  613 拍 / 153 小节（+228 拍, +51 小节）
```

与 all-in-one 的 **609 拍 / 153 小节**几乎完全一致 ✅

BPM 中位 66.67 → **130.43**。

### 速度段提取

补全后仍有 ±3% 抖动（拆分间隔时均分导致），所以切段阈值定为 **5%**：

```
演进：1%（17 段） → 2.5%（10 段） → 5%（1 段）✅
最终：bar 0–152  129.73 BPM
```

### 速度轨编辑

- 双击某个 BPM 段 → 输入框改数值 → Enter 提交
- 改完 TempoMap 重建，**网格和小节线按新速度重排**
- 实测：131.2 → 130.0 生效

### 踩过的坑：用「全局中位」判异常是错的

第一版用「偏离全局中位 > 3% 视为检测错误」，结果这首变速歌的 130 BPM 整段被当噪声剔除，速度轨只剩一段 65 BPM——**真实的倍速变化被完全抹掉**。

**教训**：一首歌可能没有单一"正常速度"。「异常」必须用**倍速关系**判断，不能用偏离度。

## 架构基石：拍时间轴是权威，秒是派生

用户明确的架构要求：

> 修改 bpm 不要影响和弦在拍时间轴上的位置，影响的是这一小节的播放标记走时速度即可。
> 举例：如果我从 60 改到 120，然后和声完全对不上了，这是正常现象。
> 分析的时候先对 bpm，再对和声在哪个拍上。
> 拍时间轴应该是最核心的基准，秒时间轴是次要的。

### 三层关系

```
ChordEvent { startTick, endTick }   ← 权威（整数 tick，永不因 BPM 变化）
        ↓ 由 TempoMap 换算
TempoMap（BPM 段）                  ← 换算参数（用户可改）
        ↓
seconds                             ← 派生（只用于播放定位）
```

**关键推论**：
- 改 BPM 时**不需要重算任何事件** —— 这是"谱面不漂移"的根本保证
- 秒只在两处出现：① 模型原始输出（换算的输入）② 喂给音频引擎的播放定位
- **数据模型里不应该把"和弦的秒位置"当权威字段**

### 实测（同一首 153 小节）

| | 和弦 tick | 第 10 小节的时间 |
|---|---|---|
| BPM 129.7 | `G:maj:0` / `D:maj/3:22080` / `E:min7:25920` | **0:20** |
| BPM 200 | **完全相同** | **0:14** |

tick 一个字节没动，只有走时速度变了 —— 所以"和声对不上"是**预期行为**。

### 分析顺序：先对 BPM，再对和声在哪一拍

**这是本节最重要的实现细节。**

旧做法（错误）：用 `TempoMap` 把和弦秒转 tick。
问题：TempoMap 由 **估计的 BPM** 派生，而 BPM 是平均值。用平均值转 153 小节的谱面，
0.5% 的 BPM 误差累积到末尾就是**半拍漂移**。

新做法：`makeBeatSnapper()` 用**实测拍点**做映射。

```ts
// 拍点秒数 → 拍序号（tick = 序号 × 960）
// 和弦秒 → 找最近拍 → 精确落在拍上
const beatSnapper = makeBeatSnapper(data.beatsSec);
```

实测结果：**9/9 个和弦边界全部精确落在拍点上**。

> 拍点是 beat_this 实测的每一拍时间；BPM 是从拍点**算出来的**平均值。
> 所以要用拍点、不要用 BPM —— 前者是测量值，后者是估计值。

### 速度轨 / 拍号轨改成「标签式」

参照 Song Master Pro 的做法（用户提供的截图）：

| 旧（块状） | 新（标签式） |
|---|---|
| 每个 BPM 段渲染成覆盖整段的色块 | 只在**段起点**打一个小标签 `♩ = 130` |
| 视觉上很吵，大色块淹没轨道 | 中间保持空白，一眼看出"哪里变了" |
| 拍号同理 | 拍号只在变化点显示 `4/4` |

这符合"BPM 是标签、拍时间轴是基准"的语义：
**BPM 标记不"拥有"一段时间区间，它只是改变从这一点开始的走时速度。**
